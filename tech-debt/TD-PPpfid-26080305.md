#201 changed the `a11y-contrast` job's "Upload Playwright report" step
(`.github/workflows/ci.yml`) to `if: always()`, so a run that fails once
and passes on Playwright's in-job retry keeps its evidence — the failing
attempt's error context and the retry's trace both reach the
`playwright-report` artifact (TD-PPpfid-26080304). That covers a retry
*within* one job run. It does not cover the other way a flaky a11y run
gets absorbed: someone sees the red required check, presses "Re-run
failed jobs", and the second attempt goes green.

On a re-run, `actions/upload-artifact@v4` uploads under the same name
without a 409 — nothing errors, and the required check reports green —
but GitHub makes the previous attempt's artifact inaccessible: the
download link disappears from the run and the old URL 404s
([actions/upload-artifact#585](https://github.com/actions/upload-artifact/issues/585),
open, no maintainer response). So the reflex response to an intermittent
a11y failure silently destroys the evidence this step now exists to
keep, and the next occurrence starts from nothing again.

Suggested fix: name the artifact per attempt —
`name: playwright-report-${{ github.run_attempt }}` on the upload step.
Verify it actually helps before settling on it: the reporter of
actions/upload-artifact#585 was already including `github.run_attempt`
in the artifact name and still lost the earlier attempt's artifact,
which suggests GitHub scopes a run's artifact list to the latest attempt
regardless of naming. The check is cheap — force a failure on a branch,
let the job go red, re-run it, then see whether attempt 1's artifact is
still listed and downloadable, both in the run's UI and via
`gh api repos/Poetic-Poems/poetic-fiddle/actions/runs/<id>/artifacts`.

If per-attempt naming doesn't survive that check, put the evidence
somewhere a re-run can't reclaim instead: a previous attempt's log and
job summary stay reachable through the run's attempt selector (confirm
this in the same experiment), so writing the axe violations into
`$GITHUB_STEP_SUMMARY` would keep a per-attempt copy of the part that
matters most. Failing that, the honest outcome is a comment on the
upload step telling whoever hits a flaky run to download the report
before re-running.

Whatever lands, keep the surrounding comments accurate: the `reporter`
comment in `playwright.config.ts` describes what the upload step
archives, and both it and the step itself currently name the artifact
`playwright-report`.

Raised in the reviewer pass on #201
([comment](https://github.com/Poetic-Poems/poetic-fiddle/pull/201#issuecomment-5165439452))
and deliberately left out of scope there, since the case
TD-PPpfid-26080304 targeted — a retry inside one job run — is fully
covered by that change.
