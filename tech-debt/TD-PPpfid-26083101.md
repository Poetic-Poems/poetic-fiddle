`handleExport` in `src/components/AccountDangerZone.tsx:91-105` delivers the archive with the create-anchor/click/revoke pattern:

```js
const url = URL.createObjectURL(blob);
const link = document.createElement("a");
link.href = url; link.download = filename;
link.click();
URL.revokeObjectURL(url);   // same task as the click
```

Two known browser footguns sit in those five lines, neither of which affects the server side of W14 (the route, its scoping, and the archive bytes are all sound and verified):

1. **Synchronous revoke.** The HTML spec runs an `<a download>` activation's fetch in parallel with the script that dispatched the click, so revoking the blob URL on the very next line is a race against the download starting. Chrome and current Firefox generally win that race; it has been reported to lose in WebKit/iOS Safari. The universal recommendation (MDN's own example, file-saver, etc.) is to defer the revoke.
2. **Detached anchor.** The link is never appended to the document. Firefox historically required an in-document anchor for a synthetic `download` click; modern Firefox is believed to handle the detached case, but appending and removing costs nothing and removes the doubt.

**Why it matters:** when either bites, it fails *silently* — `handleExport` has already resolved, so the UI shows no error and the poet simply never receives a file. This is the delivery step of a data-subject right (AC92), where a silent no-op is the worst failure mode. Nothing in the change verified the download end-to-end: the Implementer confirmed the preview deploy serves `/poems` and that the route 401s without a token, and the Reviewer verified the tar bytes and the RLS scoping, but no one exercised the click-to-file path in a real browser. `src/components/AccountDangerZone.test.tsx` mocks `HTMLAnchorElement.prototype.click` and asserts `URL.revokeObjectURL` was called, which pins the current ordering in place rather than testing that a file arrives.

**Where:** `src/components/AccountDangerZone.tsx:91-105` (`handleExport`); the test that pins the ordering is `src/components/AccountDangerZone.test.tsx` ("exports and downloads the archive via an object URL"). This is the codebase's only object-URL download path — `grep -rn 'createObjectURL' src/` returns just this one — so whatever shape it settles on becomes the house pattern for any future download (e.g. a single-poem ".poem" download).

**Suggested fixes:**
- Append the anchor to `document.body` before `click()` and remove it after, and defer the revoke to a later task (`setTimeout(() => URL.revokeObjectURL(url), 0)`, or a longer delay as file-saver uses).
- Or bypass the anchor entirely by having the route's URL be navigated to directly — not viable here, since the request needs an `Authorization` header.
- Either way, update the component test so it asserts the anchor was in the document at click time and that the revoke does not happen synchronously, rather than asserting the current ordering.

## Default: Append the anchor to `document.body`, click it, remove it, and move `URL.revokeObjectURL(url)` into a `setTimeout(..., 0)` — it is a three-line change with no downside, whereas leaving it as-is trades a silent, hard-to-diagnose delivery failure for nothing.
