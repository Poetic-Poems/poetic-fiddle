*Filed 2026-07-24, from the 2026-07-23 project review (R-27, F-DEPS-04).*
`typescript` (two majors behind) and `eslint` (one major behind) both had
Dependabot bump PRs closed unmerged with no recorded reason, unlike
jsdom's well-documented TD26071901 hold.

Fix: trial each bump; merge if clean, or record the specific breakage as a
dated entry matching jsdom's style.

*Root cause found 2026-07-31 (review R-06, F-SEC-01, F-DEPS-01):* the
`eslint` hold's blocker is now known — Dependabot PR #129
(`eslint` 9.39.5 → 10.8.0) has a maintainer comment (2026-07-27) confirming
`eslint-config-next@16.2.12` (current latest stable) bundles
`eslint-plugin-react@7.37.5`, which still calls the ESLint-10-removed
`context.getFilename()` API, so CI's lint step throws a `TypeError`; no
newer `eslint-config-next` exists yet to fix it. This is also why `npm
audit` reports 9 high-severity advisories (all one chain:
`eslint@9.39.5`'s own `minimatch@3.1.5` → `brace-expansion@1.1.16`,
GHSA-mh99-v99m-4gvg) — dev-tooling only, not reachable from any deployed
path, resolved automatically once this bump lands. The `typescript` half
remains genuinely undocumented — Dependabot's closed PR #9 has only its
generic auto-close message, no human rationale recorded.

*TypeScript root cause found 2026-08-01:* trialing PR #9's bump
(`typescript` 5.9.3 → 7.0.2, the current `latest`) shows `tsc --noEmit`
passes cleanly, but `npm run lint` fails outright: the `typescript-eslint`
`eslint-config-next` pulls in (`^8.46.0`, locked here at 8.63.0; 8.65.0 is
the current latest and declares the same range) has a `typescript` peer
range of `>=4.8.4 <6.1.0` and cannot load at all under TS 7 — 8.63.0 dies in
`@typescript-eslint/typescript-estree` with `TypeError: Cannot read
properties of undefined (reading 'Cjs')`, 8.65.0 with an explicit
`typescript-eslint does not support TS 7.0`; either way no rule ever runs
(see
[typescript-eslint#10940](https://github.com/typescript-eslint/typescript-eslint/issues/10940),
which tracks TS ≥7.1 support). No `typescript-eslint` release accepts TS 7
yet, so PR #9's silent auto-close and this bump's lint failure are the same
blocker.

That range does allow `typescript` 6.0.x, though, and `tsc --noEmit`, lint,
`next build`, and the full `vitest` suite all pass cleanly on `typescript`
6.0.3 (the latest 6.x release) — Dependabot's PR #9 skipped straight past it
to 7.0.2 rather than proposing it as its own step, which is why it went
untried. That clean intermediate is applied here (`typescript` bumped
5.9.3 → 6.0.3), closing one of the two majors this item was filed over. The
remaining hold is the same one blocking `eslint`: bumping past 6.0.x forces
a `typescript-eslint` release that doesn't exist yet.
`.github/dependabot.yml` now carries an `ignore` rule for `typescript`
`semver-major` updates, mirroring jsdom's, so Dependabot can't propose that
next major jump (6.x → 7.x) until `typescript-eslint` lifts the ceiling.

*Correction 2026-08-04 (TD-PPpfid-26080110):* the GHSA-mh99-v99m-4gvg half
of the `npm audit` findings described above did not need the `eslint` 10
bump after all — `brace-expansion`'s patched version for the 1.x line
(`1.1.17`) satisfies `minimatch@3.1.5`'s existing `^1.1.7` dependency range,
so `npm update brace-expansion` alone moved the lockfile to `1.1.18` and
cleared the advisory with a clean `npm audit --audit-level=high` over the
full tree, no `--omit=dev` needed. The `eslint` hold itself (`eslint-config-next`
still calling the ESLint-10-removed `context.getFilename()`) is unaffected
and remains open.
