*Filed 2026-08-05, from TD-PPpfid-26080402's scope: "`required-checks-drift.yml`
must not change in this item... file a new tech-debt item for it".*

`.github/workflows/required-checks-drift.yml` (weekly, Monday 06:42 UTC)
has the same gap that TD-PPpfid-26080402 closed for
`supabase-auth-drift.yml`: a detected drift between the checked-in
`.github/required-checks.yml` snapshot and the live branch rules is only a
red run in the Actions tab plus GitHub's default scheduled-failure email,
and nothing else. The sibling `td-tooling-drift.yml` files a deduplicated
issue instead — a step that exists precisely because F-CI-03 /
TD-PPpfid-26080103 judged a bare failed run insufficient for a scheduled
guard — and this repository's work is largely dispatched from open
issues, which a red scheduled run never creates.

Fix: add `issues: write` and an issue-filing step to
`required-checks-drift.yml`, mirroring `td-tooling-drift.yml`'s pattern —
dedup against open issues only, since drift is a recurring condition and
a fresh occurrence after a closed report is news again. Unlike
`scripts/check-supabase-auth-drift.mjs`,
`scripts/check-workflow-wiring.mjs --print-required`'s comparison step
already separates the "drift detected" outcome from an operational
failure (the step itself doesn't need a `continue-on-error` adaptation),
so this item's fix may be closer to `td-tooling-drift.yml`'s direct
`drifted=` output shape than to `supabase-auth-drift.yml`'s
`continue-on-error` + `steps.<id>.outcome` shape — confirm which applies
when implementing.

The trade to accept, as it was for TD-PPpfid-26080402: the step widens
the workflow's token permissions from `contents: read` alone to include
`issues: write`.
