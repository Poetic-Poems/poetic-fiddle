*Filed 2026-08-04, from the review of PR #205 (TD-PPpfid-26080301), item 1
of
https://github.com/Poetic-Poems/poetic-fiddle/pull/205#issuecomment-5166219132.*

`buildAuthDriftReport` in `scripts/check-supabase-auth-drift.mjs` compares
every allowlisted key with strict `!==`, so any representational
difference between `supabase/config.toml`'s value and the Management
API's — not only a real disagreement — reports as drift. The review
predicted two concrete cases: the API returning
`password_required_characters: null` where the committed value is `""`
(both mean "no requirement"), and a stringified number such as
`jwt_exp: "3600"`. The first materialised on the check's very first
exposure: the merge commit's `deploy` job reported
`auth.password_requirements (config.toml: "") does not match live
password_required_characters (null)` alongside five genuine
disagreements —
https://github.com/Poetic-Poems/poetic-fiddle/actions/runs/30848846269.

This matters more than a misreport because of where the pre-deploy copy
sits: ahead of `supabase db push` in `ci.yml`'s `deploy` job, so a false
positive stops migrations deploying from `main` until someone reconciles
a difference that is not real.

Behind the same key there is also a vocabulary gap: `config.toml`
expresses `password_requirements` symbolically (`letters_digits`,
`lower_upper_letters_digits`, …) while the Management API expresses the
setting as literal character classes. The mapping asserted today holds
only for "no requirement"; if a requirement is ever set, the comparison
needs a translation table between the two vocabularies.

Fix: teach the comparison the known-benign equivalences per field rather
than globally — treat live `null` as equal to committed `""` for
`password_required_characters`, coerce stringified numbers before
comparing numeric fields — and add the symbolic → character-class
translation table (or an explicit "unsupported value" failure) so a
future non-empty `password_requirements` cannot assert the wrong thing.
Keep everything not explicitly normalised loud: the check's job is still
to fail on real drift.

The five genuine disagreements in that first run (mailer autoconfirm,
SMTP max frequency, OTP length, both TOTP flags) are live-vs-file
reconciliation under TD-PPpfid-26080301's settled dashboard-stays-
authoritative model, not part of this item.

Where: `scripts/check-supabase-auth-drift.mjs` (`buildAuthDriftReport`,
`ALLOWLIST`), exercised from `.github/workflows/supabase-auth-drift.yml`
and the `deploy` job in `.github/workflows/ci.yml`.
