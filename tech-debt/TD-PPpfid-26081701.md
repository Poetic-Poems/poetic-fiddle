*Filed 2026-08-17, from the review of PR #333
(https://github.com/Poetic-Poems/poetic-fiddle/pull/333#issuecomment-5310285880).*

In `.github/workflows/td-tooling-drift.yml`'s "Compare tech-debt scripts
against poetic main" step, the per-file fetch inside the loop is unguarded:

```bash
curl -fsSL "https://raw.githubusercontent.com/Poetic-Poems/poetic/main/$f" -o /tmp/upstream
```

Under the step's `set -euo pipefail`, a non-zero `curl` aborts the step at
that iteration. The `GITHUB_OUTPUT` write happens only *after* the loop, so
`steps.diff.outputs.drifted` is never set, and both the "File an issue if
drift detected" and "Fail if drift detected" steps are gated on
`steps.diff.outputs.drifted != ''`. The result is a red job with no issue
filed, no `::error` annotation naming the failure (`curl -fsSL` is silent on
an HTTP error), and any drift detected earlier in the same loop silently
discarded — the run reports only "Process completed with exit code 22".

Simulating the step locally against a stub `curl` (manifest fetch fine, first
entry drifted, second entry 404) confirms it: the `::error file=` annotation
for the first entry is emitted, the step then aborts on the second entry's
fetch, and the `GITHUB_OUTPUT` write is never reached — so the recorded drift
on the first entry never reaches the issue-filing step.

**Why it matters.** Losing the durable issue on a failure path is the same
class of gap [TD-PPpfid-26080103](TD-PPpfid-26080103.md) was filed about (a
bare red run rather than a filed issue), and this workflow's issue-filing
step exists because that item's fix added it. This check runs weekly on a
schedule (Mondays 06:17 UTC), where a red run with no annotation and no
issue is precisely the outcome the filing step was meant to prevent.

The gap is pre-existing, but PR #333 makes it more reachable: after that
change the manifest fetched from `Poetic-Poems/poetic` main — not this
file — decides which paths are fetched, so a manifest entry that 404s
upstream is now a possible input this repository does not control. A rename
landing in poetic between its manifest update and the file move, or raw CDN
staleness, produces exactly that. The manifest fetch itself is correctly
handled: both the failed-fetch and the empty-manifest paths `exit 1` with an
`::error` annotation. Only the per-file fetch is unguarded.

**Where.** `.github/workflows/td-tooling-drift.yml`, the `curl` inside the
`while IFS= read -r f` loop of the "Compare tech-debt scripts against poetic
main" step.

**Fix.** Either option closes it; the first keeps the step's existing
single-exit shape:

1. Treat a failed per-file fetch as its own reason feeding the same
   `drifted` path — e.g. `|unfetchable` alongside the existing `|missing`
   and `|drifted` — with a matching `::error file=` annotation and a line in
   the filed issue's body, so the run still ends via "Fail if drift
   detected" rather than by aborting.
2. Write `GITHUB_OUTPUT` from a `trap … EXIT` so partial results survive an
   abort anywhere in the loop.

Whichever is chosen, the issue-body loop in the "File an issue if drift
detected" step needs a branch for the new reason, and the workflow's header
comment (which enumerates the missing/drifted outcomes) needs updating to
match.

Note this changes the step's failure semantics beyond what #329 asked for,
which is why PR #333's review flagged it rather than fixing it in place.
