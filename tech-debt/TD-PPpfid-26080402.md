*Filed 2026-08-04, from the review of PR #205 (TD-PPpfid-26080301), item 2
of
https://github.com/Poetic-Poems/poetic-fiddle/pull/205#issuecomment-5166219132.*

`.github/workflows/supabase-auth-drift.yml` (daily, 06:27 UTC) follows
`required-checks-drift.yml`'s shape, as its work order specified: a
detected drift is a red run in the Actions tab plus GitHub's default
scheduled-failure email, and nothing else. The sibling
`td-tooling-drift.yml` files a deduplicated issue instead — a step that
exists precisely because F-CI-03 / TD-PPpfid-26080103 judged a bare
failed run insufficient for a scheduled guard. Auth-config drift is at
least as consequential: it is a security-relevant disagreement with the
committed configuration, it pre-blocks the next migration deploy through
`ci.yml`'s copy of the check, and this repository's work is largely
dispatched from open issues, which a red scheduled run never creates.

Fix: add `issues: write` and an issue-filing step to
`supabase-auth-drift.yml`, mirroring `td-tooling-drift.yml`'s — dedup
against open issues only, since drift is a recurring condition and a
fresh occurrence after a closed report is news again. The pre-deploy
copy in `ci.yml`'s `deploy` job needs no such step: it fails the
required `CI` check on `main`, which is visible on its own.
`required-checks-drift.yml` predates the issue-filing pattern and has
the same gap; consider giving it the same step in the same change.

The trade acknowledged in the review, and the reason PR #205 did not
include this: the step widens the workflow's token permissions from
`contents: read` alone to include `issues: write`.
