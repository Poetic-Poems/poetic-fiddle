# Findings

This review examined poetic-fiddle across all 13 dimensions. No Critical or High-severity finding surfaced; the project remains in good health. The findings below are organised by dimension, in the checklist's order.

| Severity | Count |
|---|---|
| Critical | 0 |
| High | 0 |
| Medium | 5 |
| Low | 14 |

## Architecture and design (ARCH)

**Strengths:** The codebase has a clean, consistently-applied layering: `src/lib` holds all data-access/business logic, `src/components` is presentation, and `src/app` is routing/SSR glue. A dependency-graph check found zero circular dependencies across all 116 modules. The `poetic` framework seam (pinned release-tarball dependency, with `src/lib/poetic-css.generated.ts` regenerated by `scripts/sync-poetic-css.mjs` on every install) is a well-designed single source of truth, exercised against the real `poetic` package in both unit and e2e tests rather than mocked. Config/secrets handling is a standout: `.env.example` documents a `NEXT_PUBLIC_*` vs. server-only sensitivity-tier convention, and `docs/IMPLEMENTATION-PLAN.md` §4's "done" claims check out against the actual code and git history.

### F-ARCH-01 — Several route headings still hand-roll markup instead of using `RouteHeading` · **Low**

**Evidence:** `src/app/error.tsx:29,45,60`, `src/app/share/[share_id]/page.tsx:53,66`, `src/app/remix/[share_id]/page.tsx` (~line 40), `src/app/share/[share_id]/not-found.tsx`, `src/app/remix/[share_id]/not-found.tsx` all hand-roll the heading markup instead of using `src/components/RouteHeading.tsx`, which four other route files already use for the identical markup.

**Impact:** A visual/accessibility tweak to route headings requires updating 8 call sites by hand instead of one component; the divergence risk is real since `RouteHeading` was added specifically to fix this class of drift and new instances have since been added outside it.

**Direction:** Already tracked — GitHub issue #446 (`pw::type:tech-debt`, labelled `refined`) documents this exact gap with the same file list, verified accurate as of this revision. No recommendation filed for this review.

### F-ARCH-02 — `PoemsDashboard.tsx` inlines orchestration that `Editor.tsx`'s sibling extracts to a hook · **Low**

**Evidence:** `src/components/PoemsDashboard.tsx` (376 lines) keeps six `useState`s, two data-loading effects, an imperative focus-management subsystem, and delete/remix-default handlers all inline, whereas `Editor.tsx` extracts equivalent orchestration into the independently-tested `usePoemPersistence` hook.

**Impact:** Minor inconsistency in where "editor-adjacent" logic is expected to live; harder to unit-test in isolation from its JSX.

**Direction:** Addressed by R-06.

## Code quality and maintainability (CODE)

**Strengths:** Type discipline is excellent — `tsconfig.json` has `strict: true`, and a repo-wide grep for `any`-escape-hatches across all of `src/**/*.ts(x)` returns zero hits. Error handling is unusually disciplined: every `catch` block either rethrows a typed domain error or is a deliberately-empty catch with an explanatory comment. No TODO/FIXME/HACK markers exist anywhere in `src/`, and no meaningful dead/commented-out code was found. `npm run lint`/`typecheck`/`format:check` are all clean.

### F-CODE-01 — `use-poem-persistence.ts` is the project's highest-fan-out unit · **Low**

**Evidence:** `src/lib/use-poem-persistence.ts` (438 lines, the largest non-test source file) is a single hook with 13 `useState` calls, 4 `useEffect`s (two performing in-render `setState`), and 6 memoised async handlers orchestrating draft persistence, sign-in migration, save, share, unshare and remix-override flows in one function body.

**Impact:** Nearly every piece of `Editor.tsx`'s behaviour flows through it, so a regression here is maximally consequential; the in-render `setState` pattern (lines 197-219) is subtle enough to need dense prose comments. It is well-tested (546-line test file) and well-commented, which mitigates the risk.

**Direction:** Addressed by R-06.

### F-CODE-02 — Domain error classes repeat an identical 6-line shape across two files · **Low**

**Evidence:** `src/lib/poems-store.ts` defines nine near-identical domain error classes (lines 18-132), and `src/lib/account.ts` repeats the same shape for two more — ~70 lines of copy-pasted boilerplate with no single point of enforcement.

**Impact:** Currently consistent, but a future addition could drift (e.g. forget `this.cause = cause`) without a type-level check catching it.

**Direction:** Addressed by R-06.

## Security (SEC)

**Strengths:** The auth/authorization boundary is unusually rigorous: the account export/delete routes verify the caller's bearer token against Supabase Auth itself rather than trusting a client-supplied id; RLS policies are default-deny and correctly scoped on every table, with explicit `revoke all` from `anon`/`authenticated`; the two `security definer` RPCs (`get_shared_poem`, `bump_heartbeat`) set `search_path = ''`, closing the classic search-path hijack. The heartbeat cron secret is compared with `timingSafeEqual`. CSP uses a per-request nonce, no `unsafe-inline`, `frame-ancestors 'none'`, and a narrow `frame-src` allow-list, backed by a real-browser review checklist because string-level tests can't catch browser-level CSP breakage. Sanitisation runs through one shared DOMPurify config consumed identically by the client preview and SSR share path, with the embed URL re-validated against an explicit allow-list even though today's data can "only ever" be a safe path. No committed secrets were found.

### F-SEC-01 — No explicit CORS policy documented · **Low**

**Evidence:** No `Access-Control-Allow-Origin` header is set anywhere in the app; API routes rely on the browser's same-origin default.

**Impact:** This is the correct default (no action required for security), but undocumented — a future contributor adding a public API might assume CORS is already handled.

**Direction:** Addressed by R-07.

## Testing and quality assurance (TEST)

**Scope/method note:** `test:a11y` (Playwright + axe-core) and `test:db` (Supabase pgTAP) could not be run in this review's sandbox (no root for browser install, no Docker daemon for Supabase CLI). Both were assessed by inspection instead. `npm run coverage` was run independently and confirmed: 584/584 tests pass across 59 files, 90.46%/85.05%/90.61%/92.19% (statement/branch/function/line).

**Strengths:** The riskiest paths are well covered — the account-delete route test explicitly verifies the caller's bearer token (not a client-supplied id) is what's trusted. Tests assert observable behaviour rather than internals; `contrast.test.ts` derives its expected colours by parsing `globals.css` at test time rather than hardcoding a snapshot, so it can't silently drift from the file it checks. CI's required `ci` job depends on the unit, a11y-contrast and pgTAP suites, so none can silently stop gating merges.

### F-TEST-01 — `draft-storage.ts`'s graceful-degradation paths are untested · **Low**

**Evidence:** `src/lib/draft-storage.ts:6-11,19-23` — the private-browsing/quota-exceeded catch blocks (AC98's target behaviour) are never triggered by the test file (75% branch coverage).

**Impact:** The one scenario this code exists to handle gracefully has no regression coverage.

**Direction:** Addressed by R-05.

### F-TEST-02 — `poem-title.ts`'s defensive-typing branch is untested · **Low**

**Evidence:** `src/lib/poem-title.ts:13-19` — the non-string-title ternary branch is untested (50% branch coverage).

**Impact:** Minor — defends against upstream `poetic`'s return shape; low likelihood of firing.

**Direction:** Addressed by R-05.

### F-TEST-03 — The mobile-resize postscript-clamp fix has no test proving it still fires · **Medium**

**Evidence:** `src/components/PoemPreview.tsx:59-78` and `src/components/SharedPoemView.tsx:85-100+` both contain a `ResizeObserver`-driven debounce fixing `TD-PPpfid-26080108` (postscript clamping breaking on the mobile pane toggle). Coverage shows this body unexercised (62.5%/66.66% branch respectively).

**Impact:** This is the regression-fix path for a previously-shipped mobile bug; a future change could silently break it again with green CI.

**Direction:** Addressed by R-04.

### F-TEST-04 — A handful of `scripts/*.mjs` tooling files are the weakest-covered in the repo · **Low**

**Evidence:** `scripts/sync-poetic-css.mjs` (50%), `scripts/check-dependency-audit.mjs` (57-69%), `scripts/extract-changelog-notes.mjs` (57.69%) are the weakest-covered files in the repo.

**Impact:** Low — these are CI/tooling scripts, not app runtime code; `check-dependency-audit.mjs` deserves closer attention since it gates merges on security advisories.

**Direction:** Addressed by R-05.

## Dependencies and supply chain (DEPS)

**Strengths:** `npm audit` reports 0 vulnerabilities (prod-only and full), corroborated by the repo's own canary check (`scripts/check-dependency-audit.mjs`) that the advisory endpoint itself is responding with real data. Dependabot is configured for both `npm` and `github-actions` with weekly schedules; its three `ignore:` entries are each justified inline with a dated reason and cross-reference. The `poetic` framework dependency is a deliberate tag-pinned release-tarball URL, never a silent float.

### F-DEPS-01 — All three open Dependabot PRs have been CI-red for over a week · **Medium**

**Evidence:** As of 2026-09-28, PRs #426 (react bump, `react`≠`react-dom` version), #442 (`vitest` 5.0.1 alone) and #424 (`@vitest/coverage-v8` 5.0.1 alone) are all open, all `mergeStateStatus: BLOCKED`. #426 fails at test time ("Incompatible React versions"); #442/#424 fail `npm ci` outright (`ERESOLVE`, since `@vitest/coverage-v8@4.1.11` peer-depends on exactly `vitest@4.1.11`). `.github/dependabot.yml`'s npm block has no `groups:` stanza pairing these version-locked packages.

**Impact:** Every minor/patch bump for these packages will keep arriving broken and unmergeable until grouped, and the project has been unable to take a routine React patch for 8+ days.

**Direction:** Addressed by R-01.

## Tooling and developer experience (TOOL)

**Strengths:** README's "Development" table and "Environment & secrets" section give a complete clone-to-run path, including a documented WSL PATH gotcha. `.editorconfig`, ESLint, and Prettier are all committed and wired into CI. `.nvmrc` + `engines`/`engine-strict=true` make a Node version mismatch a hard install-time failure by design.

### F-TOOL-01 — This review's own environment could not satisfy the pinned Node version · **Low** (environmental, not a repository defect)

**Evidence:** The review sandbox had Node v26.8.2 with no alternate-version tooling, while the repo pins Node 22.x and enforces it strictly. `npm ci` required `--engine-strict=false` to proceed.

**Impact:** Not a repository defect — the strict pin worked exactly as intended. Recorded as a scope-and-method caveat: automated results in this review were produced under Node 26 rather than the pinned Node 22.

**Direction:** None — no repository change indicated.

## CI/CD and release engineering (CI)

**Strengths:** The CI design is sophisticated and well-documented: a single always-running `CI` job satisfies GitHub's "skipped but required checks" constraint while gating on conditional jobs; `workflow-wiring` self-checks that every PR-triggered job is reachable from a required check; `required-checks-drift.yml` independently re-fetches the live ruleset weekly and fails on drift from the checked-in snapshot. `CONTRIBUTING.md` includes specific, hard-won guidance (a same-tree audit red→green flip being suspicious, CSP changes needing a real-browser check).

**No new findings.** The redness on the Dependabot PRs (F-DEPS-01) is CI correctly catching real breakage, not a false positive; the two stuck items covered under GOV (F-GOV-01, F-GOV-02) are process gaps, not CI configuration defects.

## Performance and scalability (PERF)

**Strengths:** Every Supabase access point issues exactly one query per operation — no N+1 pattern found anywhere in the data-access layer. The share-page cache is correctly tag-scoped with `updateTag` invalidation on save/unshare/delete. The backend-health probe is gated ahead of the RPC specifically to avoid postgrest-js's read-retry behaviour becoming a resource-exhaustion trap. The 200ms preview/draft-save debounce matches the documented target.

**No findings.** This is a modest-traffic serverless app; no unbounded caches, synchronous I/O in request handlers, or quadratic loops were found in the sampled files. No load tests exist, but that is proportionate at this traffic tier.

## Usability and accessibility (UX)

**Strengths:** `Editor.tsx` shows careful, deliberate ARIA discipline — an explicit `aria-label` compensating for CodeMirror's React wrapper misplacing its `<label>` target, and a `tabindex="0"` added specifically for an axe-core rule gap. Save/share status, errors and the backend-unavailable banner all use `role="status"`/`role="alert"` correctly. `contrast.test.ts` (661 lines) checks actual computed contrast ratios against WCAG AA thresholds. Responsive behaviour and the documented English-only i18n scope both match reality.

### F-UX-01 — `window.location.href` navigation after account deletion (informational) · **Low**

**Evidence:** `src/components/AccountDangerZone.tsx:84` — flagged by the repo's one existing lint warning (`@next/next/no-location-assign-relative-destination`); already documented as a deliberate choice to clear all in-memory client state.

**Impact:** No meaningful accessibility downside beyond the routing concern the lint rule already names — arguably a full page load is more predictable for assistive tech than an unmanaged SPA transition. Recorded as informational, not a defect.

**Direction:** None required.

### F-UX-02 — Dialog focus-management behaviour is untested · **Low**

**Evidence:** `SignInPrompt.tsx` and `AccountDangerZone.tsx` both use native `<dialog>` (giving free focus-trapping), but no test asserts focus actually lands inside on open or returns to the triggering button on close.

**Impact:** Low — native `<dialog>` gives strong default behaviour; this is a coverage gap, not a known bug.

**Direction:** Addressed by R-05.

### F-DOC-01 — README's CI section contradicts its own "Environment & secrets" section a few lines apart · **Medium**

**Evidence:** `README.md` lines 43-48 state the `deploy` job "pushes `supabase/migrations/` to the live project on every merge to `main`" as current behaviour, but `.github/workflows/ci.yml:353` reads `if: false` — disabled since PR #428 for the same reason the "Environment & secrets" section above correctly documents (no live Supabase project). **Impact:** A reader skimming only the CI section would believe migrations auto-deploy on merge; they don't, and the two secrets it names currently gate a job that never runs. Compounds F-GOV-03/F-OPS-01 by making the docs actively misleading, not merely silent.
